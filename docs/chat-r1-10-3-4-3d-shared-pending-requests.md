## Intervenção 4.3D (primeiro incremento)
RequestsRepo tinha um timer independente de 60 s por consumidor; inFlight apenas compartilhava leituras coincidentes. Agora um stream não-replay por UID/direção/User SDK/versão de encerramento, com relógio único enquanto há consumidores. Cada entrada solicita revalidação imediata, coalescendo entradas simultâneas e chamadas ainda em voo, sem replay de decisão concluída para novo consumidor. O relógio reinicia na entrada, não acumula timers. Refcount zero remove entrada e timer; logout, troca de usuário e versão revogam, respostas antigas são descartadas, erros são propagados aos handlers existentes. Listagens one-shot e refresh explícito após mutações preservados; nenhuma autoridade de autorização passa para o cliente, nenhum TTL novo, nenhuma mudança de regras/quotas. A Promise não é abortável, o SessionReadInFlight mantém a chamada até conclusão/revogação. Consumidores já montados conservam a semântica de atualização a cada resposta, como antes; não há autorização positiva a partir de cache de nova entrada. Revalidação após mutações remotas continua limitada pelo polling existente; invalidar a partir de eventos canônicos é incremento separado, não implementado neste commit.

Testes com relógio virtual cobrem consumidores escalonados, ausência de replay, uma leitura por intervalo, separação de direções, coalescência de chamada em voo, troca de User mesmo UID, encerramento, falha e recuperação. Chromium preserva todos os 17 cenários e acrescenta critério zero HTTP 429 para getPendingFriendRequests e total observado positivo. Não impõe percentual arbitrário de redução de leituras de amizade: os números da execução serão confrontados com a base homologada. Não altera template ou contratos públicos. Sem testes locais; depende da CI.
